# Which Apple Silicon runtime should Quibble use?

Retrieved: **2026-09-06**. Directional after: **2026-09-20**. Scope: native macOS ASR and optional local writing, with low device load and useful accuracy. This is a source/code review, not a fresh runtime or energy benchmark. No new model weights were downloaded, and no App or Inference code was changed by this investigation.

## Answer

**Keep MLX Swift as Quibble’s broad local-model runtime. Add a measured Core ML path for selected speech models, starting with Parakeet, if it improves the complete dictation workload.** A universal switch to CPU, Neural Engine, or a newer library is not established as an improvement. MLX already uses Apple Silicon’s unified memory and Metal GPU; M5 GPU Neural Accelerators and the separate Neural Engine are different hardware paths. [Apple MLX/M5 explanation](https://machinelearning.apple.com/research/exploring-llms-mlx-m5), read 2026-09-06.

For model selection, expose one normal row per actual model/checkpoint and choose from tested compatible artifacts underneath it. Q4 can be a good memory-conscious MLX default; Q8 is a higher-fidelity candidate when its full working set fits comfortably. **Do not apply that rule to every runtime:** Core ML can use palettization, mixed precision, or different precision per stage. Its best shipping variant may be neither all-Q4 nor all-Q8. Apple explicitly says compression gains depend on the model, device, compute unit, and decompression strategy. [Core ML optimization guidance](https://apple.github.io/coremltools/docs-guides/source/opt-overview.html), read 2026-09-06.

The immediate engineering opportunity is clearer model/variant metadata and measured memory policy, not replacing the working transcription pipeline wholesale. The proposals below preserve the current guarded vocabulary and delivery behavior.

## What the hardware evidence actually says

**GPU and ANE are not interchangeable labels.** MLX operations use CPU/GPU memory directly; Core ML’s `cpuAndNeuralEngine` allows those two units but is not proof every operation executes on ANE. Apple offers Xcode performance reports and `MLComputePlan` to inspect operation support and preferred placement. The actual end-to-end run still needs timing and energy measurement. [MLX memory](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html), [compute units](https://developer.apple.com/documentation/coreml/mlcomputeunits), [Core ML profiling](https://developer.apple.com/videos/play/wwdc2024/10161/), read 2026-09-06.

**There is a relevant controlled comparison, and it does not support an all-ANE rule.** FluidAudio reports the following on 100 LibriSpeech test-clean files on an unspecified M-series Mac:

| Parakeet v3 encoder configuration | Publisher-reported result |
| --- | --- |
| Shipped 6-bit palette, ANE vs GPU | Same 2.6% average WER; GPU placement approximately 8% faster end to end |
| Shipped 6-bit vs INT4 encoder | 2.6% vs 5.4% average WER; INT4 also slower in its full pipeline |

This makes Parakeet a good matched-backend experiment, while rejecting the assumption that fewer bits always improve speed. The document motivates ANE for power-sensitive use but does not establish Quibble’s joules-per-dictation or battery effect. [Pinned placement experiment](https://github.com/FluidInference/FluidAudio/blob/5c19d5e12320e22bbfb7a1877b089d2665a69add/Documentation/ASR/EncoderComputePlacement.md), read 2026-09-06.

**Core ML can trade load cost against warm performance.** WhisperKit exposes sequential prewarming to reduce specialization peak memory at the cost of an extra load pass. That is a reason to display a real Preparing state after download and measure cold, cached-load, and warm cases separately. It is not a reason to pin every model in memory. [WhisperKit prewarm implementation notes](https://github.com/argmaxinc/argmax-oss-swift/blob/ea872ffd35705aa757f33033500b9b0d40bd38df/Sources/WhisperKit/Core/Configurations.swift), read 2026-09-06.

**Cohere Core ML exists, but its older measurements are not a migration promise.** FluidAudio’s model index and code now default to a static-shape v2 decoder, while `Documentation/ASR/Cohere.md` still describes the old dynamic FP16 decoder and substantial cold-start cost. The single-window API has a 35-second model window; its `transcribeLong` handles longer input. A Quibble adapter must preserve every section rather than passing our 60-second section into a truncating single-window call. Benchmark the current v2 artifacts before recommending them. [Current pipeline](https://github.com/FluidInference/FluidAudio/blob/5c19d5e12320e22bbfb7a1877b089d2665a69add/Sources/FluidAudio/ASR/Cohere/CoherePipeline.swift), [model index](https://github.com/FluidInference/FluidAudio/blob/5c19d5e12320e22bbfb7a1877b089d2665a69add/Documentation/Models.md), [older benchmark notes](https://github.com/FluidInference/FluidAudio/blob/5c19d5e12320e22bbfb7a1877b089d2665a69add/Documentation/ASR/Cohere.md), read 2026-09-06.

## Model variants: a practical policy

The following is a proposed Quibble design, not an already evaluated automatic policy. It responds to the user’s request for one model row, memory-aware choice, and preferred official weights.

1. **Separate model identity from artifact identity.** Keep family/version/parameter size as the user-facing model. Put backend, quantization, revision, bytes, conversion source, minimum OS and runtime requirements in its Details variants. Qwen 0.6B and 1.7B are different models; Qwen 1.7B Q4 and Q8 are variants of one model.
2. **Prefer publisher-hosted compatible artifacts.** A publisher’s original PyTorch checkpoint establishes provenance but may require a compatible MLX/Core ML conversion. Label publisher weights and community conversion separately, pin both, and retain notices. Never call a community conversion “official” merely because its base model is official.
3. **Pick only among validated variants.** For a given MLX model, start with a tested Q4 low-load option; prefer Q8 where measured quality benefit warrants its measured working set and the system has headroom. Respect a manual choice and the already installed working variant. Do not silently redownload/switch weights because free RAM changed.
4. **Budget the entire workflow.** Include ASR, vocabulary helper, cleanup/instruction model, activations, caches and load peak, plus reserve for the user’s other apps. Total physical RAM alone is an inadequate estimator. For now any RAM threshold must be labeled a heuristic until measured on smaller Macs. Store known measured peaks per exact artifact/runtime version.
5. **Use backend-specific compression.** Core ML may favor a 6-bit palettized encoder or mixed precision. Apple notes weight decompression can occur before or during execution, so download bytes are not a trustworthy runtime-memory estimate. [Apple compression behavior](https://apple.github.io/coremltools/docs-guides/source/opt-overview.html), read 2026-09-06.

Expose the result simply: for example **Recommended for this Mac**, with the chosen variant and download size in secondary text, and a separate “Other variants” disclosure. Keep the quality score independent from weight precision. No RAM cutoffs or Q4/Q8 accuracy equivalence were proven by this investigation.

## Dependency freshness and architecture checks

- Current `mlx-audio-swift` upstream HEAD matches our pin `bf14ae0c…` as of this read. A dependency update alone will not expose its other models: Quibble needs an adapter, compatible artifacts, capability semantics, download handling, and tests. [Pinned models directory](https://github.com/Blaizzy/mlx-audio-swift/tree/bf14ae0c26e4e85553dd989571cae29d70fa6735/Sources/MLXAudioSTT/Models), checked via GitHub API 2026-09-06.
- **MLX core** latest release is `v0.32.2`; **MLX Swift** latest published tag is `0.31.6`. Swift main `ab924c82…` updates the core to 0.32.2, which is not the same thing as a released Swift 0.32.2. New core kernel work merits a controlled dependency experiment, not an assumed ASR speedup. [Core release](https://github.com/ml-explore/mlx/releases/tag/v0.32.2), [Swift release](https://github.com/ml-explore/mlx-swift/releases/tag/0.31.6), [Swift main commit](https://github.com/ml-explore/mlx-swift/commit/ab924c82ead3b970caaa1c0ac11171de23f0305a), read 2026-09-06.
- Swift 0.31.5 raised its package tools version to 6.3. The selected local Xcode reports **Apple Swift 6.3.3**, so that particular requirement is satisfied here; external build requirements still need updating when dependencies change. [Swift 0.31.5 release note](https://github.com/ml-explore/mlx-swift/releases/tag/0.31.5), plus local `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcrun swift --version`, read/run 2026-09-06.
- The pinned Granite Speech adapter is a Conformer → QFormer → autoregressive Granite LLM architecture, documented for Granite 4.0 1B Speech. This does not establish compatibility with a newly named TurboCTC checkpoint. Do not wire a new model to an old adapter solely because “Granite” matches. [Pinned Granite architecture](https://github.com/Blaizzy/mlx-audio-swift/blob/bf14ae0c26e4e85553dd989571cae29d70fa6735/Sources/MLXAudioSTT/Models/GraniteSpeech/GraniteSpeech.swift), [supported model README](https://github.com/Blaizzy/mlx-audio-swift/blob/bf14ae0c26e4e85553dd989571cae29d70fa6735/Sources/MLXAudioSTT/Models/GraniteSpeech/README.md), read 2026-09-06.
